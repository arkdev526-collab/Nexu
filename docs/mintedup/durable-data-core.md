# Minted Up Durable Data Core

## Purpose

Minted Up originally stores its entire prototype database in `.data/mintedup/db.json`. That is useful for local development but cannot be treated as production persistence on Vercel: serverless instances do not share that filesystem and a later invocation is not guaranteed to see an earlier write.

The Durable Data Core introduces an explicit store boundary while preserving the existing domain API:

```ts
await read((db) => ...)
await mutate((db) => ...)
```

No marketplace, auction, research or Source Library module has to know whether the backing store is local JSON or Postgres.

## First Postgres shape

The first migration deliberately uses one Postgres table and one JSONB aggregate row:

```text
mintedup_state
  id = 1
  revision
  payload jsonb
  created_at
  updated_at
```

This is a migration bridge, not the final relational schema. It gives Minted Up a shared durable source of truth with minimal domain churn. Once stable, high-write/high-query areas such as orders, bids, sessions, source records and learning events can move to dedicated tables behind the same storage boundary.

## Concurrency

Every write:

1. reads the current payload + revision;
2. clones and mutates the payload using the existing callback;
3. performs `UPDATE ... WHERE revision = expected_revision RETURNING revision`;
4. retries against the new state if another instance won the race.

This compare-and-swap model prevents lost updates across multiple Vercel instances without requiring an interactive database session.

### Mutate callback rule

A Postgres conflict may replay a `mutate()` callback. A callback must therefore change only the supplied draft / derive its return value from that draft. Irreversible external work (charging a card, sending an email, uploading a blob) must happen behind a separate idempotent boundary rather than inside `mutate()`.

## Explicit backend selection

Minted Up never switches storage merely because a generic `DATABASE_URL` exists.

Local/default:

```text
MINTEDUP_STORE_BACKEND=file
```

Postgres cutover:

```text
MINTEDUP_STORE_BACKEND=postgres
MINTEDUP_DATABASE_URL=postgresql://...
```

`DATABASE_URL` and `POSTGRES_URL` are accepted fallbacks only after the backend has explicitly been selected as Postgres.

If `MINTEDUP_STORE_BACKEND=postgres` is selected but the connection is invalid/missing, Minted Up fails visibly. It does **not** fall back to a private file database.

## Neon / Vercel

The concrete HTTP adapter targets `@neondatabase/serverless` 1.1.0. It is loaded only when the Postgres backend is actually used, so the existing branch can remain green before infrastructure cutover.

Before activating Postgres, install the runtime driver in the repository and commit the resulting package-lock change:

```bash
npm install @neondatabase/serverless@1.1.0
```

Then provision a Neon Postgres database (directly or through the Vercel Neon integration), add the connection string, and apply the migration.

The driver dependency is intentionally not faked or vendored into this update. Production activation must have a reproducible package-lock generated by npm.

## Migration commands

After the driver is installed:

```bash
npm run db:migrate
```

This creates `mintedup_state` if allowed by the database role and initialises row `id=1`.

To import an existing local snapshot into an empty Postgres state:

```bash
npm run db:import
```

Custom file:

```bash
npm run db:import -- --file=/path/to/db.json
```

The import refuses to overwrite non-empty Postgres state. `--force` exists for deliberate recovery/admin use only.

For production deployments it is preferable to run `migrations/mintedup/001_durable_state.sql` through the database migration process rather than grant the web runtime schema-creation permission. `MINTEDUP_POSTGRES_AUTO_MIGRATE=1` is available for controlled environments, not as the default.

## Scheduled ingestion

The old `MINTEDUP_DURABLE_STORE=1` assertion is no longer trusted. Scheduled ingestion now considers storage durable only when:

```text
MINTEDUP_STORE_BACKEND=postgres
```

and a valid Postgres connection string is present.

The existing scheduled-ingestion gates still require:

```text
MINTEDUP_ENABLE_SCHEDULED_INGESTION=1
MINTEDUP_CRON_PRIMARY=1
```

and the cron secret once the scheduler is allowed to write.

## Current limitation: image bytes

This migration makes marketplace/research/source **data** durable. Listing images are still written under `.data/mintedup/uploads`. Therefore object storage remains a production release gate. The admin Data Core page reports this separately so a green Postgres status cannot be mistaken for complete storage readiness.

## Capacity / next relational phase

The Neon HTTP driver has a bounded HTTP response size, and serialising the whole aggregate row on every mutation is not the long-term high-volume design. Before the JSONB aggregate approaches material size/latency limits, move these domains into relational tables in roughly this order:

1. sessions + users;
2. orders + ledger + payment events;
3. listings + bids + auctions;
4. source records + research documents;
5. learning events / append-only telemetry.

The point of this first cutover is to make persistence real **without** combining the infrastructure migration with five independent domain rewrites.
